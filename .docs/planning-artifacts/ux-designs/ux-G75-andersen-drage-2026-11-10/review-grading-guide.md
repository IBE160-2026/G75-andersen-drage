# Examiner review: Design and user experience (criterion 4, 10%)

## How the examiner will actually grade this

The guide is clear about the order of work (section 3). Step 4, "Vurder design", happens **in the running app**, right after step 2 (follow the README) and step 3 (test the core flows, including bad input). The planning documents are not read until step 6. So the A–B descriptor for criterion 4 ("gjennomarbeidet, konsistent og intuitiv … grunnleggende tilgjengelighet er ivaretatt") is earned or lost on the built screens. The spines can only earn the sixth bullet ("spor av designarbeid") directly. For everything else they are a promise that I will check against the app.

If the app does not run from the README, I grade from code, tests, **screenshots and video in the repo** (section 3, last paragraph). Right now the repo has no screenshots of anything. The only visual artifacts are an Excalidraw JSON file, which GitHub shows as raw text, and an HTML file that has to be downloaded to see. Both sit in a dot-folder inside a dot-folder.

Today (2026-11-12) the repo has no architecture, no epics, no code and no app. Everything below is a prediction: *if the app is built as specified, and the evidence below is visible by 2026-12-15*.

## Findings

### 4.1 Consistent visual style

- **[high]** Two modes double the consistency surface, and the spine fixes only the colors. Kveldsmodus changes chrome typography (sans 600, UPPERCASE tracked labels), elevation (shadows on the card and dialogs) and brand weight. Every screen and state has to be checked twice. Anything not checked in dark mode (dialogs, error blocks, drop zone, disabled buttons, the scrim) is where I will find inconsistency. (DESIGN.md › Brand & Style, Elevation; EXPERIENCE.md › Foundation "dark 'Kveldsmodus' (Should)") *Fix:* Ship light only until every Must flow is complete and screenshotted. Then add dark through CSS custom properties only, and before calling it done, screenshot every screen in both modes side by side.
- **[high]** 11 components are marked † ("not drawn, composed from tokens `[ASSUMPTION]`"). Among them are every surface the examiner hits in step 3 "feil input": the drop zone, the text area, the error message, the empty state, generation progress, the dialog, the Quiz Question and the banner. The parts that were drawn (top bar, Flashcard, source panel) are the ones least likely to be inconsistent. (DESIGN.md › Components, †) *Fix:* Run step 4 of the agreed Finalize plan ("key-screen mocks") before architecture. At minimum mock Start (empty + error), Genererer, Quiz answered, Resultat, Consent dialog, and the 360px Round.
- **[medium]** Disabled, hover, pressed and loading states for buttons, quiz options and the drop zone have no visual spec. EXPERIENCE.md requires "disabled while pending (NFR-8)" and "inline loading" for Explain Simpler, so the AI-assisted build will invent these per screen. (DESIGN.md › Components › Button) *Fix:* Add one row of interaction-state tokens (disabled opacity or color, hover tint, a loading spinner or skeleton) that every component reuses.
- **[low]** The mockup still says "Torsa's" and shows the Quote on the card front. This drift is disclosed in the spine, but it is the only colored drawing an examiner might open. (.working/directions-4.html title and hero) *Fix:* Leave the history as it is, but add a one-line banner at the top of the HTML: "Exploration 2026-11-10; superseded by DESIGN.md".

### 4.2 Navigation and information architecture

- **[high]** The top bar on mobile is "condensed `[ASSUMPTION]`", but it carries brand, Note name, Readiness Score, the gap note, the theme toggle and 'Innstillinger'. At 360px this either wraps or overflows. It is the first thing I see when I resize. (EXPERIENCE.md › Component Patterns › Top bar; DESIGN.md › Top bar) *Fix:* Specify the 360px top bar now: brand plus an overflow menu (theme, Innstillinger), with the score on its own line or moved into the Notatoversikt header.
- **[medium]** The route back to Start from Notatoversikt and the Round is "browser Back and … brand link `[ASSUMPTION]`". A brand link is not discoverable, and leaving mid-Round silently creates an interrupted Round. I will ask: "how do I get back to my notes?" (EXPERIENCE.md › Information Architecture, "Back navigation") *Fix:* Add a visible 'Dine notater' breadcrumb or back link on screens 4–7, and say that leaving a Round keeps it as resumable.
- **[medium]** Arkiv is reachable only through "a link at the bottom of 'Dine notater' (for now)". After archiving, the row disappears with no feedback, so a first-time user does not know where it went. (EXPERIENCE.md › Note Lifecycle, Flow 4 step 2) *Fix:* After archiving, show a toast "Arkivert. [Angre] · [Vis arkiv]". It gives feedback (4.3) and makes the archive discoverable (4.2) in one move.
- **[medium]** The IA wireframe predates Arkiv, the first-run Consent gate and the Note-row controls. It shows Consent at "Første innsending" with 'Godta · Bruk demo i stedet'. In the UJ-1 flow, Start comes before Consent, and the consent text says "Ingenting lagres hos oss". (.working/ia-2026-11-10.excalidraw; .working/flow-uj1-2026-11-10.excalidraw screen 2) *Fix:* Add a dated v2 of the IA (keep v1 as a process trace) showing Arkiv, Samtykke-first and Innstillinger contents.
- **[low]** 'Eksamen om en time' (FR-20, Should) is listed in the Notatoversikt IA row but has no component, state or flow anywhere. (EXPERIENCE.md › IA row 4) *Fix:* Either specify it or move it explicitly to "not in v1" so the entry point is hidden, as the priority rule requires.

### 4.3 Feedback, errors and empty states

- **[high]** English and Norwegian are mixed inside the spine's own behavior tables. State Patterns and UJ-3 quote "No API key configured — use demo mode or add a key to .env", "All key concepts are known — this is a review round", "No readable text found" and "File could not be read". Explain Simpler cites "Could not make a verified simpler explanation". A dev agent that implements from State Patterns will ship English strings into a bokmål UI (NFR-9). That is exactly the inconsistency I see in step 3. (EXPERIENCE.md lines for State Patterns "No API key", "Review round", "Input rejected"; Component Patterns › Explain Simpler; UJ-3 Failure) *Fix:* Replace every English string in State Patterns, Component Patterns and the flows with a microcopy key (`err.noKey`, `round.review`, `err.noText`, `err.unreadable`, `simpler.fail`). The microcopy table should be the single source.
- **[medium]** Stale `[OPEN]` markers contradict the Microcopy table: the "Advance control label `[OPEN]`" (`quiz.next` exists), the "Submit button labelled `[OPEN]`" (`start.paste.submit` exists), "Empty — Arkiv … copy `[OPEN]`" (`archive.empty` exists) and "Review round … Norwegian copy `[OPEN]`" (`round.review` exists). To an examiner, internal contradictions look like a document generated once and not maintained (warning sign 2). (EXPERIENCE.md › Component Patterns Quiz Question and Text area; State Patterns) *Fix:* Remove the four stale `[OPEN]`s.
- **[medium]** All microcopy is "draft by Claude … awaiting Tor's approval `[ASSUMPTION]`". If it is never visibly approved, the strongest 4.3 evidence reads as unreviewed AI output. (EXPERIENCE.md › Microcopy) *Fix:* Review the strings, change at least a few, record the approval and the changes in the memlog, and remove the caveat. That edit is also evidence for criterion 1.
- **[medium]** Archiving gives no feedback. The row just disappears. The 'Arkiver' icon button sits next to the row hit-area, and there is no undo. (EXPERIENCE.md › Interaction Primitives "archiving has no confirmation"; Flow 4) *Fix:* Use the undo toast from 4.2.
- **[low]** There is no success or confirmation feedback for export/import, theme switch persistence, or Consent withdrawal in Innstillinger. Only the failure strings exist. (EXPERIENCE.md › Microcopy) *Fix:* Add three short success strings.
- **[low]** "Klar: –" appears in UJ-1 step 5 and the wireframe, while DESIGN says "No score shown when there are zero eligible concepts". It is unclear whether a fresh Note shows "–", nothing, or 0 %. (EXPERIENCE.md UJ-1 step 5; DESIGN.md › Readiness Score) *Fix:* Define the pre-first-Round state of the Readiness Score in Microcopy.

### 4.4 Basic accessibility

- **[high]** Nothing in the plan puts accessibility *evidence* in the repo. The guide asks me to judge accessibility, and the PRD reconciliation (row 4.4) already flagged that NFR-6 lacks a verification method. The spine names "axe … no serious/critical violations" and "manual keyboard checklist", but not where the results are stored. I will tab through two screens. If I hit one trap, I will not trust the claim. (EXPERIENCE.md › Accessibility Floor) *Fix:* Commit the axe report (or a Playwright + axe test) and a filled-in keyboard checklist for UJ-1 and UJ-3 under .docs, and link both from the README.
- **[medium]** The quiz option keys are `[OPEN]`, while flashcards have Space/1/2 with visible hints. A mouse-free quiz therefore depends on Tab order through four options, and keyboard behavior differs between Round screens. (EXPERIENCE.md › Interaction Primitives) *Fix:* Decide A–D or 1–4 (watch the clash with 1/2 marking on the preceding screen) and show the hints.
- **[medium]** The focus path after a reference jump is unclear. "Focus moves to the target Passage; … Shift+Tab path returns to the Item `[ASSUMPTION]`". On desktop the stated Tab order is source panel before study panel, so Shift+Tab from a Passage goes further *up* the source, not back to the card. A keyboard user loses their place in a Round. (EXPERIENCE.md › Accessibility Floor; Interaction Primitives "Tab order") *Fix:* Add a visible "Tilbake til kortet" control on desktop too (the same pattern as the mobile return toast), and move focus back explicitly.
- **[medium]** The theme toggle and 'Arkiver' are icon-only, and their accessible names are required only in prose. The importance badge "cycles on click", so the state change has to be announced. Alt text as such is barely relevant (there are no content images), but I will check icon buttons for names. (DESIGN.md › Theme toggle; EXPERIENCE.md › Importance badge) *Fix:* State `aria-pressed` or a live announcement for the badge cycle, and give exact accessible-name strings in Microcopy for every icon button.
- **[low]** Passage IDs and keyboard hints use 11px mono, and chips 12px. Contrast passes, but "lesbar" in the guide is about legibility as well as ratio. (DESIGN.md › Typography mono, chip) *Fix:* Raise mono to 12px, as the spine already did for `reference`.
- **[low]** `lang` for generated content is `[OPEN]`. A Norwegian UI over an English Note will be read with the wrong voice by screen readers. (EXPERIENCE.md › Accessibility Floor) *Fix:* Set `lang` on the source panel and the study content from the Note's detected language.

### 4.5 Screen sizes

- **[high]** The only mobile visual is one 360px Kilde-tab frame in directions-4.html. Start with its drop zone and Note rows (title + meta + badge + 'Arkiver' at 360px), the Consent dialog, the quiz with four full-width options, and Resultat have no mobile drawing. These are the screens I will resize. (DESIGN.md › Layout & Spacing; EXPERIENCE.md › Responsive & Platform) *Fix:* Wireframe a 360px Start (with rows), Quiz (answered) and Resultat, and screenshot them from the built app.
- **[medium]** The breakpoint is 768px `[ASSUMPTION]` with a `1fr : 1.15fr` split. Between 768px and about 1000px each column is about 350–450px wide, and a 26px serif card front plus a source panel will feel cramped. There is no tablet behavior. (DESIGN.md › Layout; EXPERIENCE.md › Breakpoint) *Fix:* Either raise the split breakpoint to about 1024px (tabs below), or state a minimum source-panel width and test at 800px.
- **[low]** Drag-and-drop is the drop-zone primary on mobile, where dropping is not possible. (DESIGN.md › Drop zone) *Fix:* On touch devices show only "Velg fil".

Embed the IA, the UJ-1 flow and the final screenshots in the README under a "Design" heading with links to DESIGN.md, EXPERIENCE.md and the memlog.

Wireframes that contradict the delivered app on Consent timing, consent wording and Arkiv will look like early exploration that was abandoned, not design that drove the build. These are six `[NOTE FOR PRD]` items. The PRD is `status: final` and contains none of them. Section 5 warns about planning documents that "beskriver en annen app enn den som er levert". Here the PRD will describe *less* than the app, and the DR-4 traceability (stories → FR-IDs) has no FR for these surfaces. (EXPERIENCE.md › Open Items; prd.md) *Fix:* Run the planned `bmad-prd` update now. Add FRs for Note list, archive and importance, and record the change reason, citing the memlog dates.

A draft spine at the deadline reads as a document "generert én gang og ikke brukt videre". Tor's own voice is visible only in the memlog ("Tor's words", "Tor asks for an option…"), and some memlog assumptions are still unconfirmed (stakes, "du" form, peeking). (EXPERIENCE.md passim; .memlog.md line 9) *Fix:* Have Tor confirm or reject the outstanding assumptions in one pass and log it. Keep a short human-written "Design decisions" summary (5–8 bullets, linked from the README) that points to memlog entries.
- **[medium]** Uncommitted changes. DESIGN.md, EXPERIENCE.md and .memlog.md are modified in the working tree. The design history on GitHub is only as good as what is committed, with dates. (git status) *Fix:* Commit the Finalize work in small, described commits (pre-mortem changes, error color, microcopy), not as one lump.

### Cross-cutting: scope against the solo deadline

- **[critical]** Today is 2026-11-12 and the deadline is 2026-12-15, so about 33 days remain for a solo developer with no architecture, epics or code. The UX defines 10 surfaces, a Consent gate, Demo Mode with Fixtures, an AI pipeline with Quote Check, two visual modes, archive/restore/delete, importance sorting, export/import, mobile tabs with a return toast, and an accessibility verification. Criterion 4 punishes *half-finished* UI harder than *missing* Should features: a dead or unstyled Arkiv or a broken dark mode is the "inkonsistent" I will cite. The priority rule (hide cut entry points) is right, but it is written as an `[ASSUMPTION]`. (EXPERIENCE.md › Information Architecture › Priority) *Fix:* Make the Must/Should line a firm plan with a date. For example, Must flows UJ-1 and UJ-3 working and screenshotted by about 2026-12-01, and Should items only after that. Remove the `[ASSUMPTION]` from the "hide, never dead" rule, and record cuts in the PRD and README.
